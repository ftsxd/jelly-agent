# Jelly Agent 代码项目创建、同步与 Agent 分配方案

**版本：** V2.3（后台同步、目录范围与代码现状对齐）  
**日期：** 2026-09-15  
**定位：** 当前开发范围，以本版本为准。本版已按实际代码核对，第 2 节给出逐项对照。

## 1. 本期目标

实现一个简单可用的流程：

**创建代码项目 → 同步仓库 → 分配给 Agent → Agent 读取并分析。**

当前重点是创建和同步，分配采用简单的项目与 Agent 关联。权限体系后续单独建设。

此前的服务级授权、审批、有效期、结果与记忆隔离等方案保留在[后续扩展参考](monorepo-code-analysis-future-design.md)，不作为本期开发和验收门槛。

### 为什么之前拉不下来

两处叠加，导致 Silkworm 这种规模的仓库首次同步必然失败，这是本版最先解决的问题：

1. 同步在 HTTP 请求里**同步执行**，并且用的是请求自己的 context。浏览器超时、关闭标签页、反向代理断连都会取消正在进行的 clone。
2. 超时 3 分钟、上限 512 MB / 100000 文件。实测 Silkworm 工作树（不含 `.git`）约 **400 MB / 18119 个文件**：文件数没问题，体积贴着上限，3 分钟拉 400 MB 也不够。

## 3. Silkworm 怎么接

已只读检查 `/Users/mingjing/coding/silkworm`。它是一个 Git 仓库，实际业务目录为 `services/`，有 126 个一级候选目录；`common/`、`gateway/`、`ad/` 也被服务代码引用。

**支持整仓分析，也支持按子目录创建代码项目。首版同步选定分支的整个仓库，通过项目配置决定 Agent 分析哪些目录。**

```text
代码项目：Silkworm 优惠券
├── 仓库地址：创建时填写
├── 分支：创建时选择
├── 主分析目录：services/discount_coupon
├── 补充参考目录：common/、ad/（按需选择）
├── 代码存储：平台统一同步管理
└── 分配 Agent：例如 CodeAnalyst
```

无需一次创建 126 个项目。按实际分析需要创建即可：同一个 Silkworm 仓库可以配置“优惠券分析”“支付分析”等项目，分别选择子目录，分配给相同或不同的 Agent。需要整仓分析时选择仓库根目录。

这里区分两个范围，两者独立：

- **同步范围＝整个仓库。** 每个代码项目各拉一份完整工作树，独立记录 Commit。
- **分析范围＝主分析目录及显式选择的参考目录。** 它只决定 Agent 能读到什么，不减少下载量。

按 Silkworm 的实测体量（工作树约 400 MB / 18119 文件），代价是明确的：

| 项目数 | 磁盘占用 | 首次同步 |
|---|---|---|
| 1 个 Silkworm 项目 | ~400 MB | 分钟级 |
| 3 个（优惠券 / 支付 / 其他） | ~1.2 GB | 各自分钟级 |

**这是已确认接受的取舍。** 换来的是：改目录配置、加参考目录、改业务描述都**不需要重新同步**，跨目录追查引用时随时能扩范围。稀疏拉取（`git clone --filter=blob:none --sparse` + `sparse-checkout set`）是第 9 节后续优化的第一项——它能把单个项目压到几 MB、秒级完成，代价是每次改目录配置都要重拉。

同步范围与分配的 Agent 数量无关：一个项目只有一份快照，分配给一个还是五个 Agent 都共用它。

例如：

> 分析优惠券项目中 services/discount_coupon 的相关逻辑，必要时查看已配置的 common/ 和 ad/ 参考代码。

默认只添加主分析目录，不自动开放全部同仓代码。发现跨服务引用但未配置对应参考目录时，Agent 提示缺少上下文，由用户编辑项目补充目录，无需增加审批流程。

本地分支 `master` 只是盘点结果，正式接入分支由创建项目时选择。本地目录不等于已经配置远端地址和凭据。[服务候选清单](silkworm-service-inventory.md) 继续作为仓库结构参考。

## 4. 页面和操作

左侧保留“代码”入口，本期只做项目列表、新建/编辑表单和同步记录。

### 项目列表

| 展示信息 | 内容 |
|---|---|
| 项目 | 名称、仓库地址、分支、主分析目录 |
| 同步 | 待同步、排队中、拉取代码中、成功、失败、中断可重试 |
| 版本 | 最近成功的 Commit 和时间 |
| Agent | 已分配 Agent 或未分配 |
| 操作 | 同步最新代码、编辑、分配 Agent、查看同步记录 |

### 创建项目

| 字段 | 说明 |
|---|---|
| 项目名称 | 如 Silkworm |
| 项目标识 | 唯一标识，可由名称生成后确认 |
| 仓库地址 | 首版沿用现有 HTTPS 支持 |
| 分支 | 如 master、main，由用户选择 |
| 主分析目录 | 仓库内相对目录，如 services/discount_coupon；填 . 表示整仓 |
| 补充参考目录 | 可选，可添加多个，如 common/、ad/ 或其他服务的 proto 目录 |
| 目录名称与描述 | 每个主目录、参考目录都可填写业务名称和职责说明，详见下节 |
| 凭据引用 | 私有仓库使用已有服务端环境变量名 |
| Git 用户名 | 按 Git 平台认证要求填写，可选 |
| 分配 Agent | 从现有 Agent 列表选择，可稍后分配 |
| 项目说明 | 可选，说明用途或重点目录 |

提供两个按钮：

- **保存**：保存配置，稍后同步。
- **保存并同步**：保存配置后立即创建首次同步任务。

代码存储位置由平台生成，不要求用户填写服务器路径。项目可以先同步完成，再分配 Agent。

首次创建可手填子目录，同步成功后可从目录树选择。同步完成后校验配置的目录存在且确实为目录；不存在时显示具体路径并允许修正，不能显示为可分析。已有快照时保存即校验，问题当场暴露，不用等到 Agent 搜出空结果才发现。

路径必须是仓库内相对路径，拒绝绝对路径、越界路径、反斜杠和符号链接逃逸。页面保留仓库相对路径，便于查看跨目录引用。

### 子目录名称与业务描述

每个配置的目录包含三个信息：**目录路径、业务名称、业务描述**。主分析目录与参考目录使用相同的编辑方式。

以下为配置示例，`services/order` 是用户举例，不代表已在 Silkworm 盘点中确认存在：

| 字段 | 示例 | 作用 |
|---|---|---|
| 目录路径 | services/order | 定位代码，仍按实际仓库目录校验 |
| 业务名称 | 订单服务 | 页面和 Agent 使用的易读名称 |
| 业务描述 | 负责订单创建、查询、取消和状态流转；支付处理在独立支付服务中。 | 说明职责和边界，具体内容由用户填写 |

页面显示“订单服务 · services/order”，展开后查看描述。名称与描述均可选，未填名称时显示目录名。项目说明描述整个分析项目的用途；目录描述解释具体代码目录的职责，两者分别保存。

用户说“分析订单服务”时，Agent 根据已分配项目中的名称、描述和路径定位候选目录，再读取实际代码核实。出现多个同名候选时结合项目和路径消歧，不能默认选中任意目录。描述作为用户维护的业务背景，不作为已经从代码验证的事实，也不会自动增加代码访问范围。

编辑名称或描述只保存平台配置，无需重新拉取代码；下一次项目列表或目录信息读取返回最新说明。Git 同步不覆盖这些人工说明。实际目录被移动或删除时提示重新选择路径，保留原说明供用户修正。

## 5. 同步过程

### 首次同步

1. 校验并保存项目配置。
2. 创建同步记录，立即返回任务编号。
3. 服务内部后台执行 Git 拉取，不占用浏览器请求等待完成。
4. 在临时目录准备代码，读取实际 Commit。
5. 校验主分析目录和参考目录存在，完整成功后发布可分析目录，更新状态和时间。
6. 页面显示“已就绪”，分配的 Agent 可以读取代码。

页面状态直接读项目上持久化的 `sync_state`：

```text
待同步 → 排队中(queued) → 拉取代码(running) → 成功(succeeded)
                                    ├→ 失败(failed)，可重试
                                    └→ 中断(interrupted)，服务重启造成，可重试
```

同步接口返回 `202` 和 `task_id`。同一项目已有任务时返回**同一个** `task_id`，不会产生第二次拉取。

### 更新与失败处理

- 点击“同步最新代码”创建后台任务。
- 同一项目已有同步任务时，返回已有任务，避免重复拉取。
- 新版本完整可用后再切换，Agent 不读取半成品。
- 更新失败保留上一份成功代码，明确提示“当前使用旧版本”。
- 展示仓库无法访问、分支不存在、凭据无效、超时或磁盘不足等可理解的错误。
- 刷新、关闭页面不取消已创建的后台同步。
- 服务重启后，中断任务标记为“中断，可重试”；首版不要求自动断点续传。

### 实现保持简单

后台任务运行在现有 Go 服务内，不引入独立消息队列或分布式 Worker。

拉取用的 context **与 HTTP 请求脱钩**（`context.WithoutCancel`），这是关键的一条：此前用请求 context 意味着关标签页就取消 clone。任务状态随项目一起落盘，不是内存里的「同步中」标志；进程启动时把残留的 `queued` / `running` 一次性改写为 `interrupted`，否则重启后项目会永远显示同步中、且所有修改都被 busy 锁挡住。

上限按「整仓拉一个微服务大仓库」重新定，并且可配置：

| 配置项 | 默认值 | 旧值 | 为什么改 |
|---|---|---|---|
| `files.code_projects.sync_timeout_sec` | 1800（30 分钟） | 180 | 3 分钟拉 400 MB 不够 |
| `files.code_projects.max_snapshot_mb` | 2048 | 512 | Silkworm 已占 400 MB，贴着旧上限 |
| `files.code_projects.max_snapshot_files` | 200000 | 100000 | 18119 文件尚有余量，一并对齐 |
| `files.code_projects.history_depth` | 50 | 1（隐含） | 深度 1 意味着只有快照没有历史，`git log`/`diff` 无从答起 |

超限的报错要指向可操作的下一步（调哪个配置项，或改用只含所需目录的项目），不是把内部错误原文抛给用户。

首版沿用重新拉取并发布目录的方式。共享 Git 缓存、增量 fetch、稀疏拉取、定时同步和 Webhook 后续优化。

一次分析使用确定的成功版本；新同步完成后，新分析读取新版本。正在使用的旧代码目录保留到分析结束后清理。这里仅保证读取正确性，不建设历史快照或任务审批页面。

## 6. 分配给 Agent

页面选择负责分析的 Agent，例如：

```text
Silkworm 优惠券（services/discount_coupon）→ CouponAnalyst
Silkworm 支付（services/silkworm_pay）→ PaymentAnalyst
其他代码项目 → CodeAnalyst
```

一个 Agent 可以关联多个项目。本期项目表单只选择一个负责 Agent，不设有效期；需要多 Agent 共享时再扩展交互。

运行时：

- Agent 的代码项目列表来自平台保存的关联关系。
- 只向代码工具提供已分配、已同步项目。
- 本期分配单位是代码项目，项目可以代表整仓或某个子目录及其参考目录。
- 浏览、搜索和读取统一按配置目录过滤；仓库相对路径保持不变，父目录仅作为导航节点，不列出其他兄弟目录。不能只靠提示词要求 Agent 遵守目录范围。
- 未同步时返回“尚未同步”，不读取空目录。
- 取消或更换分配后，后续读取使用新的关联关系。

沿用现有只读工具：`list_code_projects`、`list_project_dir`、`grep_project_files`、`read_project_file`，以及读提交历史的 `log_project_commits`、`show_project_commit`、`diff_project_revisions`。

历史工具读的是同步留下的裸对象缓存（快照里没有 `.git`），因此不联网、不用凭据；pathspec 同样钉死在配置目录上——diff 的内容就是文件本身，范围外的改动不出现在列表里，也不出现在 patch 里。能看多远由 `history_depth` 决定，结果里始终带着本地提交数与 `shallow` 标记，避免把同步深度说成仓库的全部历史。

`list_code_projects` 返回项目中已配置目录的路径、业务名称、描述及主目录/参考目录角色。Agent 因此能将“订单服务”等业务叫法映射到实际路径，无需用户每次重述。仅返回当前已分配且可见目录的说明，且不返回仓库地址、凭据变量名和快照目录名。

### 范围过滤怎么实现

「不能只靠提示词」需要落到机制上。做法是：**快照目录仍是唯一的 root，在它之上加一层仓库相对前缀白名单**（`NewScopedRoot`）。一个路径必须同时在 root 之内**且**在某个前缀之内才可达，两层检查都在符号链接解析之后进行。

不把主目录和参考目录各自当成一个 root，原因很具体：多 root 时路径展示会加上目录名前缀，Agent 读回的路径就不再是仓库相对路径，而这恰好是它能引用 `services/order/handler.go` 并让这个引用在工具之外仍然成立的前提。

三个入口都要覆盖，少一个就是绕过：

| 入口 | 处理 |
|---|---|
| 显式传路径（读取 / 列目录 / 限定搜索） | 路径解析时做前缀检查 |
| 搜索不传路径 | 「全部」解释为已配置的各个目录，不是它们所在的仓库 |
| 从导航祖先开始遍历 | 遍历时跳过范围外目录 |

导航祖先单独处理：范围是 `services/discount_coupon` 时，`services` 可以列出，但**只显示通往范围的那个子目录**，不显示其余 125 个兄弟目录。把整仓结构摊给模型，等于既泄露了仓库形状，又在诱导它去试读不该读的路径。

同名前缀不算包含：`services/order` 不会顺带放行 `services/orders`。

未配置目录的旧项目（`root_path` 缺省）继续按整仓分析，升级不受影响。

分析采用先搜索再读取，结果保留项目、Commit、文件和行号，便于复核。不需要先完成全部服务建模或自动依赖图。

主分析目录和参考目录都来自该项目同一份成功代码版本。修改目录配置时先校验，再原子更新；后续工具读取使用新范围，已返回的内容不会被收回。若将来提供终端或执行工具，不能直接暴露整仓目录并声称仍具备相同的范围限制；本期仅承诺上述项目只读工具的范围控制。

这只是基本的项目关联和工具可见范围，不宣称已完成会话、记忆、外部 MCP 的跨 Agent 数据隔离。界面使用“分配 Agent”，不出现审批、有效期等本期不建设的流程。

## 7. 对当前原型的最小调整

| 位置 | 本期工作 |
|---|---|
| 创建表单 | 主分析目录、可选参考目录、各目录名称与描述、保存、保存并同步、可选 Agent |
| 同步接口 | 从请求中等待改为后台执行，与请求 context 脱钩，返回任务编号 |
| 同步状态 | 状态随项目落盘，支持页面恢复、错误展示、重试和重启后的中断标记 |
| 同步上限 | 超时与体积/文件数上限按整仓拉取重新定，并可配置 |
| 分配交互 | 简化为选择 Agent，取消本期操作中的期限和审批概念 |
| 代码读取 | 按项目关联与目录配置提供代码，在工具层统一过滤浏览、搜索、读取三个入口 |
| 版本切换 | 不暴露未完成目录，不删除正在分析的版本 |
| Silkworm 接入 | 按需创建整仓或子目录项目，显式添加需要的同仓参考目录 |

数据仅需项目配置、同步记录及项目中的 Agent 关联。沿用当前已有存储方式，不为本期引入完整权限表、审批表和服务策略表。

项目配置增加以下字段，旧项目缺省时保持原有行为：

| 字段 | 默认 | 说明 |
|---|---|---|
| `root_path` | `.` | 主分析目录。缺省即整仓分析，旧项目不受影响 |
| `reference_paths` | `[]` | 补充参考目录 |
| `directory_metadata` | `{}` | 以规范化仓库相对路径为键的名称与描述 |
| `dir_issues` | `[]` | 最近一次校验中缺失或不是目录的配置路径 |
| `sync_state` | `""` | `queued` / `running` / `succeeded` / `failed` / `interrupted` |
| `sync_task_id` | `""` | 进行中的任务编号，结束后清空 |
| `sync_started_at` | `null` | 本次任务开始时间 |

保存时路径统一规范化（去掉尾部斜杠和冗余段），`directory_metadata` 的键按同样规则规范化，两者因此始终对得上。

`directory_metadata` 的形态：

```json
{
  "root_path": "services/order",
  "reference_paths": ["common"],
  "directory_metadata": {
    "services/order": {
      "name": "订单服务",
      "description": "负责订单创建、查询、取消和状态流转。"
    },
    "common": {
      "name": "公共组件",
      "description": "各服务共用的基础组件，分析依赖时参考。"
    }
  }
}
```

### 标注按仓库存，不按项目存

「`services/order` 是订单服务」是关于**仓库**的事实，不是关于项目的。按项目存会出问题：同一个 Silkworm 仓库通常会建多个项目（优惠券、支付），每个都要标一遍、自动生成也要各花一遍 token，两次产出的描述还不一致，改了一边另一边不会跟着变。

所以标注存在独立的 `code-projects/annotations.json`，以规范化的仓库地址为键：

```json
{
  "annotations": {
    "https://e.coding.net/realmicro/realmicro/silkworm": {
      "services/order": { "name": "订单服务", "description": "…", "tags": ["核心链路"] }
    }
  },
  "drafts": { "…": { } }
}
```

仓库地址规范化后比较：大小写、结尾的 `/` 和 `.git` 不构成不同仓库。

**共享不等于放开范围。** 读取时按各自项目的分析范围过滤：主目录是 `services/discount_coupon` 的项目看不到 `services/silkworm_pay` 的标注，也标不了 —— 与 `list_project_dir` 不列出兄弟目录是同一条规则。写入同样受范围约束。

标注范围是**分析范围内的任意目录**，不限于主目录和参考目录：整仓项目只有一个配置目录，按旧规则 130 个服务只能写一条说明。范围内的目录本来就可读，标注它不扩大任何权限；范围外的一律拒绝，否则说明就成了第二条指定路径的途径。

`projects.json` 里不再保存标注——那是配置文件，改一条标注不该算作改项目配置。旧版本存在项目上的标注在进程启动时自动迁移，迁移后从 `projects.json` 移除。删除项目时，只有当没有其他项目引用同一仓库，才清掉该仓库的标注。

草稿（Agent 提交、等待人工采纳）同样按仓库存，且**不进入任何读工具**，采纳后才并入正式标注。

接口复用 `/api/code-projects`。同步接口从「等待完成返回 200」改为「立即返回 202 + `task_id`」，状态随项目列表一起返回，不额外开查询接口。项目删除复用现有接口，同步进行中先阻止删除，避免与文件清理竞争。

仍保留基本工程处理：凭据不进入日志和 Agent 上下文；文件工具限制到项目目录；拉取不执行仓库脚本；同步有超时和磁盘限制；管理页面复用现有登录。

授权的有效期字段（`expires_at`）在后端**保留**：旧数据里的临时授权继续按期失效，`RevokeAgent` 在删除 Agent 时照常收回。页面不再提供有效期选项，只选一个负责 Agent。不自动更改用户已有分配，也不将所有仓库直接开放给所有 Agent。

## 8. 实施顺序与验收

### 实施顺序

按依赖排，把「拉不下来」排在最前——后面几步都建立在能拉到代码上：

1. 放宽超时与体积上限，并做成可配置。
2. 后台同步、任务编号、状态落盘、重启标记中断。
3. `root_path` / `reference_paths` / `directory_metadata` 的数据结构与校验。
4. 工具层的目录范围过滤（解析、无路径搜索、遍历三个入口）。
5. 工具接入范围，`list_code_projects` 带出目录说明。
6. 页面：目录表单、同步状态、分配 Agent。
7. 用真实 Silkworm 仓库验证同步和一次具体服务分析。

第 1–6 步均有单元测试覆盖；第 7 步需要远端地址和凭据，本地目录盘点不能替代。

### 验收

| 场景 | 通过标准 |
|---|---|
| 创建项目 | 能保存仓库、分支、目录配置和凭据引用 |
| 子目录项目 | 同仓不同目录可创建不同项目并分别分配 Agent |
| 目录说明 | 主目录、参考目录均可保存名称和描述，页面与 Agent 工具能读取 |
| 说明更新 | 修改说明无需重新同步；后续 Git 同步不覆盖人工说明 |
| 业务名称定位 | Agent 能依据“订单服务”等名称定位候选目录，重名时按项目和路径消歧 |
| 目录校验 | 不存在的目录提示修正；绝对路径、越界路径和符号链接逃逸被拒绝 |
| 工具范围 | 浏览、搜索和读取均只返回主目录与参考目录内的文件 |
| 首次同步 | 后台成功，页面显示 Commit 和时间 |
| 关闭页面 | 同步继续，再打开能查看状态 |
| 重复同步 | 不产生重复拉取任务 |
| 同步失败 | 原因明确，修正后可重试 |
| 更新失败 | 上一份成功代码仍可分析，并标明旧版本 |
| 分配 Agent | Agent 能发现项目并读取代码 |
| 分析具体服务 | 能定位主目录及已配置的同仓参考代码；缺失依赖时提示补充目录 |
| 同步与分析并行 | 不读半成品，不误删正在使用的代码 |
| 更换分配 | 后续读取遵循新关联 |
| 服务重启 | 中断的任务标记为“中断，可重试”，不会永远显示同步中 |
| 目录配置变更 | 改目录、名称、描述后快照保留，无需重新同步 |
| 兄弟目录不可见 | 列出 `services` 只出现已配置的那个服务，不出现其余 125 个 |
| 旧项目兼容 | 未配置目录的项目继续整仓分析 |

真实远端地址、凭据引用和负责 Agent 需要接入时填写；本地目录盘点不替代远端连通性验证。

## 9. 后续再做

优先级最高的是**稀疏拉取**：`git clone --filter=blob:none --sparse` 加 `sparse-checkout set` 已配置目录，能把单个 Silkworm 子目录项目从 400 MB 压到几 MB、从分钟级压到秒级。代价是每次改目录配置要重拉一次（几秒），以及跨目录追查引用时需要先把目录加进配置。等到磁盘占用或首次同步时间真的构成问题时再做。

其后按实际使用需要增加定时/Webhook、增量 fetch、同仓共享缓存、多个 Agent 共享项目、按身份配置的服务或路径权限、临时授权、审批、多用户角色及结果/记忆隔离。

**当前决定：优先完成创建和同步，支持按子目录配置代码项目并分配给选定 Agent；补充依赖目录由用户按需选择，权限体系后续单独建设。**
