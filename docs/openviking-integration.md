# Jelly Agent 接入 OpenViking 方案

状态：设计提案，尚未实现、安装或部署。更新日期：2026-09-10。

## 1. 推荐结论

已确认的目标：知识、长期记忆和 Skills 统一由 OpenViking 管理，作为 Agent 在线使用这些内容的权威来源，通过 Go 客户端访问 HTTP API。Jelly 负责身份授权、上下文装配、执行、审批和审计；会话运行状态仍保存在现有数据库。

本地知识、记忆和 Skill 副本仅用于迁移过渡、受控缓存和离线兜底，不长期维护另一套可独立修改的内容库。Git 可以保留原始知识及 Skill 源码的审核历史，但发布后的在线内容统一从 OpenViking 获取。

分阶段落地：先接入只读运维知识库，随后完成远程 Skills 发布与加载，再接入经过身份隔离和质量控制的长期记忆。分阶段只控制上线风险，不改变统一管理的最终目标。第一阶段不新增 Elasticsearch，也不立即删除现有全文检索。OpenViking 不代替日志平台、指标平台、CMDB 或业务数据库。

本文中模块名、工具名、配置项、阈值和排期均为拟议设计；上游能力以链接文档为依据，实施时必须锁定服务端及 SDK 版本并做契约测试，不能直接跟随 main/latest。

## 2. 与现有系统如何分工

| 数据或能力 | 归属 | 设计理由 |
| --- | --- | --- |
| Agent 编排、子 Agent、工具执行与审批 | Jelly Agent | 不引入第二套执行运行时 |
| 当前对话、任务状态、审计记录 | 现有 SQLite / PostgreSQL | 保持现有恢复、查询和审计语义 |
| USER.md / MEMORY.md 中的用户事实与偏好 | 迁移到 OpenViking 私有记忆 | 本地仅保留迁移期副本及缓存，避免双写权威源 |
| ENVIRONMENT.md 中的环境知识 | 迁移到 OpenViking 受控知识域 | 与实时状态、凭据及执行策略分离 |
| 系统指令、执行权限和安全策略 | Jelly 配置 | 不是可被自动抽取覆盖的记忆；迁移前从上述文件中拆分 |
| 运维手册、架构文档、已确认故障案例 | OpenViking resources | 统一语义检索、摘要和来源引用 |
| 用户偏好、跨会话经验 | OpenViking 私有记忆 | 长期记忆阶段上线，先解决身份、写入质量与删除问题 |
| 日志、指标、Trace、实时服务状态 | 原有观测平台及工具 | 知识用于提出排查路径，实时工具用于验证 |
| 工具原始结果与证据句柄 | 现有 record / gateway | 不把大量日志重复写入知识库 |
| Skills 定义、正文及辅助文件 | OpenViking | 统一发布、检索和加载；本地只缓存已批准版本 |
| Skill 的实际执行 | Jelly 运行时及沙箱 | 远端内容不能自行授予工具权限或获取凭据 |
| 当前全文会话检索 | 保留，作为可配置回退 | 与知识检索语义不同，验证后再决定是否退役 |

简化部署关系：

```text
CLI / Web / 钉钉 / 微信 / 定时任务
                 │
          Jelly Agent 运行时
          ├─ 工具网关 → 运维系统 / 审批 / 审计
          ├─ 本地数据库 → 会话 / 任务 / 证据 / 同步队列
          └─ 上下文适配层 → OpenViking HTTP 服务
                              ├─ 知识、长期记忆、Skills
                              ├─ 向量索引
                              └─ Embedding / 内容处理模型
```

## 3. 为什么主链路选择 HTTP，而不是只挂 MCP

OpenViking 当前已有官方 Go SDK，它本身就是服务端 HTTP 客户端，支持检索、资源和会话等操作。优先评估并封装该 SDK；若锁定版本缺少必要接口，再局部使用 HTTP，不把上游类型传遍业务代码。[官方 Go SDK](https://github.com/volcengine/OpenViking/blob/main/sdk/go/README.md)

我们的关键需求是每轮自动检索、可靠异步写入、用户隔离和故障回退。这些应由运行时确定执行，而不是依赖模型是否调用工具。MCP 可用于独立体验验证或管理员诊断，但第一阶段不同时暴露一整套 OpenViking MCP 工具，避免重复检索及绕过权限控制。

拟新增窄接口，而非通用数据库框架：

- `KnowledgeBackend`：限定范围检索、受控内容读取。
- `MemorySink`：追加已筛选消息、提交抽取、查询处理状态；长期记忆阶段启用。
- `SkillRegistry`：查找授权技能、获取已批准内容及辅助文件、校验发布版本和撤销状态。
- `KnowledgePublisher`：受审批的资源导入和案例发布，与在线只读工具分离。

应用自己的返回结构至少包含 URI、标题、摘要、来源、修订标识、适用环境和可信状态。上游缺失字段由 Jelly 的来源登记表补充，不假定所有字段都可直接存进上游任意 metadata。

## 4. 知识组织与更新

首批只导入运维手册、系统架构和已确认的复盘文档。建议逻辑目录：

```text
viking://resources/ops/
├─ runbooks/        排查、回滚、恢复手册
├─ architecture/    服务关系和架构说明
├─ environments/    非敏感环境说明，不是实时 CMDB
└─ cases/           经过确认的故障案例
```

这里的 resources 是账号内共享知识域，不意味着公开上网。不同团队、项目或环境需要独立授权范围；不能把目录命名、标签或提示词当作访问控制。

每篇文档在 Jelly 侧登记：`source_id`、来源 URL/仓库路径、原始修订号、内容哈希、负责人、适用服务/环境、审核状态、有效期、OpenViking URI、导入任务与状态。原始文档继续以 Git、文档系统或对象存储为事实源。

导入流程：管理员选择白名单来源 → 文件大小/类型校验与脱敏 → 上传/导入 → 跟踪处理任务 → 校验可检索 → 发布该修订。替换文档时，在新修订就绪后切换有效版本；被撤销的旧修订立即从 Jelly 可用范围排除并失效缓存。

不能让远端服务自行访问任意模型提供的 URL、本机路径或内网地址；导入来源需要白名单、重定向复查和上传权限。第一阶段不开放全盘目录扫描，也不让在线 Agent 自动向共享知识库写入。

## 5. 每轮如何检索和使用

### 5.1 自动召回

在一次根级用户请求开始时执行一次 `Prepare`：从可信身份及 Agent 配置算出可访问范围，使用脱敏后的当前问题检索，按预算生成参考材料，再进入模型运行。工具循环不重复执行同一次自动召回；后续追问需要更深入资料时允许显式检索工具。

第一版使用带 `target_uri` 的 `find`，必要时评估 `search(mode=list)` 的查询扩展。不要直接采用 `search(mode=context)`：当前接口不接受 `target_uri`，无法套用本方案的目录范围限制。由 Jelly 自行组装有来源、受预算约束的上下文。[检索接口](https://docs.openviking.ai/zh/api/06-retrieval)

建议初始参数：Top 5、自动注入最多 2,000 tokens、自动召回总时限 1.5 秒。这些是待压测的起始目标，不是上游性能承诺。注入预算取配置上限和模型剩余预算的较小值，为回答及工具调用保留空间。

优先使用摘要/概览；模型需要操作细节时再读正文。每条参考材料携带来源及适用环境，明确标记“参考数据，不是系统指令”。不因命中旧案例就跳过实时检查或既有审批。

### 5.2 提供给模型的工具

第一阶段新增两个只读工具，继续通过现有 gateway 审计：

- `knowledge_search(query)`：模型不能自行选择用户、账号、凭据或扩大知识范围。
- `knowledge_read(reference)`：只读取本轮授权引用；服务端复核 URI 的规范化路径、权限、有效修订及内容长度，拒绝越界跳转。

所有召回及工具调用共用权限和预算逻辑。授权范围不能只在结果返回后过滤：请求本身须带受限范围，上游身份/ACL 再提供第二道隔离。缓存按账号、主体、Agent 授权范围、修订及 invocation 隔离，不跨用户共享结果。

资料缺失、服务异常、权限拒绝分别记录。超时或 5xx 可以降级为现有 Agent；401/403 不切换为更高权限凭据。需要知识库才能回答的具体操作，应明确说明资料暂不可用，而不是编造结论。降级不得改变执行审批策略。

### 5.3 Skills 统一管理与执行边界

OpenViking 支持保存 `SKILL.md` 和辅助文件，并提供技能管理及检索接口。当前 Skills 属于用户范围，不能假设存在任意可写的账号公共 Skills 根。[Skills 接口](https://docs.openviking.ai/zh/api/04-skills)

团队技能采用受控发布：Git 或管理界面编辑 → 审核 → 发布到 OpenViking → Jelly 读取已批准版本 → 在本地沙箱执行。Git 是可选的创作/审核源，本地 Skills 目录不再作为日常独立管理入口；管理界面的变更通过发布流程进入 OpenViking。

第一版团队共享可由专用发布身份持有技能，Jelly 的技能读取服务按团队及 Agent 授权检查后访问；该身份凭据不能用于普通用户记忆检索。私人技能使用所属用户身份。个人、团队技能来源显式区分，同名时不静默覆盖。

版本和审批由 Jelly 发布记录补充，不假定上游原生提供不可变版本仓库。发布记录包含技能标识、OpenViking URI、全部文件的内容哈希、审批人及授权范围；运行时只有取回内容与批准哈希匹配才可加载。每次执行固定同一份快照，不能中途读取更新后的脚本。

加载过程复用 Jelly 原有 Skill 调用机制：按需检索候选 → 检查发布和授权 → 加载完整说明及必要辅助文件 → 校验依赖和权限 → 执行。不会仅凭摘要执行，也不会因 Skill 声明了 `allowed_tools` 就扩大 Jelly 已授予的权限。新增依赖安装、网络访问及高风险工具调用继续走现有控制。

脚本及辅助文件下载到隔离缓存目录，限制包大小、文件类型和路径，拒绝路径穿越及越界符号链接；凭据由运行时按权限提供，不随 Skill 文件存储。缓存按身份、授权范围和内容哈希隔离。

离线兜底仅允许未过期、已批准且明确允许离线使用的快照；无法确认撤销状态时不执行高风险技能。缓存失效、无匹配版本或权限拒绝时明确报错，不回退到任意旧的本地同名技能。审计记录实际运行的 URI、哈希、发布版本和结果。

## 6. 长期记忆：后续阶段开启

### 6.1 身份是前置条件

当前 `internal/engine/engine.go` 固定 `UserID = "local-user"`；平台回调只携带会话键和文本，并没有完整发送者身份。这足以支撑原有单用户模式，但不能直接当作多人长期记忆隔离。

第一阶段只允许可信单用户或明确共享范围的团队知识读取；不向 OpenViking 捕获各平台的私人对话。长期记忆上线前增加可信入口身份对象，至少包含部署、平台、机器人绑定、会话、发送者及会话类型。不能让模型提供这些值。

个人记忆主体绑定真实认证用户；群聊使用独立群组范围，不把群内所有人合并成一个人的偏好。不自动跨平台合并用户，跨平台关联须通过明确绑定。远端会话 ID 使用稳定、不含明文敏感身份的映射，并纳入平台、机器人绑定和根 Agent，避免不同机器人会话键碰撞。

常规 `api_key` 模式使用绑定账号/用户的用户密钥；账号与用户由密钥确定。管理密钥与业务密钥分开，不能拿 root 密钥充当日常数据访问凭据。只有明确部署了可信身份网关后才考虑 trusted 头部转发；peer 过滤也不能替代完整用户隔离。[身份与多租户](https://docs.openviking.ai/zh/concepts/11-multi-tenant)

现有 MCP 连接及客户端可能被并发复用，不能通过修改共享 headers 切换用户。适配层必须使用不可变身份配置或明确的逐请求身份传递。

### 6.2 写入内容与可信度

自动捕获默认关闭。开启后，只捕获成功结束的一轮中筛选后的用户文本与最终回答；不采集推理内容、系统提示、注入的知识片段、原始工具大结果、密钥及完整日志。取消或失败的半轮不默认抽取长期记忆。

自动抽取的内容属于未审核私有记忆，不能自动成为共享运维结论。模型说“可能是连接池耗尽”不等于根因已验证。

共享案例采用显式发布流程：草稿 → 用户或管理员确认 → 发布。至少记录现象、环境、验证过的原因、实际动作、验证结果、回滚方法和来源。Jelly 保存来源登记及最小脱敏证据快照；当前工具证据默认保留期为 7 天，不能只保存一个随后过期的 `e1` 引用。

### 6.3 可靠写入与抽取

引入统一 `Prepare → Run → Finalize` 根级生命周期，覆盖 CLI、Web、钉钉、微信和定时任务。`Finalize` 只执行一次，保存同步任务，不在每个子 Agent 结束时提交，也不等待远端抽取才结束流式响应。

新增本地持久队列（outbox），由受管理的后台 worker 同步；不能只启动一个请求结束后可能丢失的 goroutine。先持久化本轮完成状态，再排队；若无法与会话写入共用事务，启动及周期性对账扫描补齐已完成但未排队的轮次。

按远端账号/主体/会话串行同步增量事件，保存事件游标、内容哈希、批次号及处理阶段。现有 `AddSessionToMemory` 每轮删除后重建本地索引，不能原样映射为远端追加整个历史，否则每轮都会重复写入。

上游支持批量消息写入和会话 commit；commit 的接受响应不等于记忆已经可用，必须追踪返回的后台任务。首版由 Jelly 单独调度 commit，关闭另一套自动触发，避免双重调度。[会话接口](https://docs.openviking.ai/zh/api/05-sessions)

建议一组成功轮次或会话空闲后批量 commit，不逐个 token 或每条工具消息提交。worker 区分“待发送、发送结果不明、已追加、已提交、抽取完成、失败待处理”。模型费用、抽取积压、重试次数均设上限。

本地去重不等于远端恰好一次写入。目前不假定上游提供客户端消息幂等键。网络超时且服务端可能已写入时，暂停该会话后续写入并核对远端内容/计数及本地批次；无法可靠核对时进入待人工处理，不能盲目重试追加或 commit。实施阶段须通过故障注入验证这一语义。

### 6.4 删除与“忘记”

本地 `forget`、删除会话、删除远端会话、删除已抽取记忆是不同动作，不能对用户统称“已经全部忘记”。

迁移完成后，`remember` / `forget` 及记忆编辑界面统一操作 OpenViking，成功写入后失效本地缓存；网络不可用时显示待同步或失败，不报告已保存。原有本地 Core Memory 内容先按主体、隐私与系统策略分类迁移，校验完成后停止本地独立写入，避免双份注入和冲突。

新建统一删除任务：先写删除标记并停止该范围的待同步任务，再清理远端关联内容、缓存和本地映射；同步 worker 必须检查删除标记，防止删除后重试复活数据。源于多个会话的合并记忆需要单独处理，不能只删源会话。

完整自动记忆上线前，必须验证派生记忆来源追踪及删除闭环；若锁定版本无法可靠实现，保持自动捕获关闭，只开放可明确定位的人工发布知识。备份也需保留期和删除策略，恢复后重新应用删除标记。

| `docker-compose.yml` | 后续新增可选 OpenViking 服务及独立数据卷 |

现有 `BuildAgent*`、`Search()` 和 `NewRunner()` 接口依赖具体 `*memory.Search`。第一阶段不必为只读知识库重写整套 ADK MemoryService；知识能力独立接入，待会话记忆迁移阶段再抽象，避免把资源搜索硬塞进全文会话索引。

新 worker 必须遵守现有 engine pin/retire 的生命周期：热更新后旧请求仍可完成，旧 worker 停止领取新工作并排空/安全释放；不能在运行中的请求使用数据库时提前关闭它，也不能让新旧 worker 无锁重复消费。

配置草案如下，当前程序尚不识别这些字段：

```yaml
context:                         # 知识、记忆和 Skills 共用连接及模式
  backend: openviking
  mode: shadow                   # off / shadow / on
  endpoint: http://openviking:1933
  api_key: ${OPENVIKING_USER_KEY}  # 仅适用于第一阶段单可信身份
  knowledge_roots:              # 记忆与 Skills 范围另由可信身份/发布授权决定
    - viking://resources/ops
  recall:
    timeout: 1500ms
    top_k: 5
    max_tokens: 2000
  capture:
    enabled: false
  skills:
    enabled: false              # 完成远程发布和加载验收后开启
    require_approved: true
```

`off` 不访问 OpenViking；`shadow` 仅记录独立检索评估，不向模型注入结果、不暴露新知识工具、不加载远程 Skills，也不隐式捕获会话；`on` 才参与回答。Skills、自动记忆仍有各自开关及上线门槛。全文检索回退单独配置，不将两套结果不加区分地重复注入。

## 8. 部署、观测与成本

第一阶段采用单独容器及本地持久存储，服务可与 Agent 同机，也可部署到内网服务器。这里“本地”指 OpenViking 服务宿主机的持久卷，不必是运行 CLI 的电脑。

为 OpenViking 单独创建命名卷，按官方镜像持久化目录挂载，并只读挂载配置。不要放在现有整目录挂给 Jelly 的 `./data` 内，避免 Agent 的文件工具接触底层索引文件。关闭附带 Bot（`OPENVIKING_WITH_BOT=0`），保留 Jelly 为唯一对话入口。[部署指南](https://docs.openviking.ai/zh/guides/03-deployment)

固定版本/镜像摘要；HTTP 端口只对应用内网开放，跨主机加 TLS 和网络访问限制。配置 Embedding 及内容处理模型的独立凭据、限额和数据出网规则：自托管文件不代表模型处理不出网。文档和对话是否可以发给模型提供商，应在试点前确定。

初期不另接 ES 或远程向量数据库。容量、重建耗时或可用性达到实际瓶颈后，再评估该版本明确支持的后端；不能假定任何“HTTP 向量库”均兼容。单实例本地存储也不等于高可用，多副本共享一个卷不能直接当 HA 方案。

复用已有观测体系，记录检索耗时/错误/命中率、注入 tokens、资料引用、导入任务状态、同步积压/最长延迟、抽取失败和模型成本。默认不记录知识正文、对话正文或凭据；来源 URI 也按敏感性脱敏。

健康检查与就绪检查分开；单篇资料的处理任务状态单独追踪。知识服务不可用不应直接让 Agent 全部不可用，但管理界面须明确显示降级和积压状态。

## 9. 迁移与退出方案

不要把可迁移性理解成“复制向量库就能换任何产品”。计划保留三类独立资产：原始文档和 Skill 源码及版本；Jelly 的来源、发布审批、身份映射和删除记录；OpenViking 的知识、记忆、Skills 正文及全部辅助文件导出。本地运行缓存不充当备份。

OVPack 可导出内容，完整账号内容备份使用 backup/restore。它不包含账号/API Key、运行队列和部分内部控制数据，也不是原子快照；需要一致性时暂停写入。dense 向量复用有模型配置兼容条件，hybrid 快照另有限制，因此退出计划默认接受重新向量化。[OVPack 迁移与备份](https://docs.openviking.ai/zh/guides/09-ovpack)

建议每日加密备份，试点保留 7 个日备份、4 个周备份，并验证访问隔离及删除要求；这是初始策略，正式 RPO/RTO 以演练结果确认。另行备份服务配置、模型版本、Jelly 数据库和恢复步骤，凭据由密钥管理系统重建。

上线前必须完成一次退出演练：

1. 暂停导入、捕获和后台写入，等待正在执行的任务稳定。
2. 导出 OpenViking 内容及 Jelly 来源/审核记录，校验数量和哈希。
3. 在隔离环境恢复，重建必要身份及索引，验证权限和检索问题集。
4. 抽样把知识与记忆转为普通文本及 JSON 来源记录，恢复 Skill 完整目录并校验哈希，确认不用 OpenViking 仍可读取核心资产。
5. 切回 `off`，验证原有对话、工具及全文检索不受影响。

更换产品时需要重建检索索引、调整排序及客户端适配；无需重新录入原始知识，但不承诺零成本迁移或原检索效果完全一致。

## 10. 分阶段交付与验收

### 阶段 A：只读试点

部署独立实例，导入少量脱敏运维文档；完成 SDK/服务端契约检查、限定范围搜索、正文读取与 shadow 评估。保持自动记忆关闭，不改现有会话存储。

准备至少 30 个真实运维问题，覆盖已知故障、架构定位、相似但不同环境、知识缺失、过期手册、恶意文档指令。以人工标注相关资料为标准，初始目标为“有答案问题 Top 5 命中率至少 85%”；对比现有方案的正确性、引用及延迟，未达标就调数据或检索，不直接全量启用。

### 阶段 B：只读正式接入

通过 gateway 暴露两个受控工具，自动召回参与回答，完善管理端导入状态、撤销与备份。以少量授权用户灰度；不增加 ES，不关闭现有全文检索。

必须通过：越权结果泄漏为零；召回预算不会挤掉必要回答空间；知识服务断开后仍能对话及使用工具；401/403 不扩大权限；撤销文档不再被引用；热更新和流式取消无资源提前关闭。

### 阶段 C：Skills 统一管理

导入现有 Skills 及辅助文件，建立发布身份、批准版本和授权映射；将现有管理界面与加载入口切换到 OpenViking，本地变为只读运行缓存。先灰度少量技能，再覆盖全部技能，不另建长期并行的本地管理库。

必须通过：说明及辅助文件完整迁移；只加载批准哈希；同轮固定版本；未授权技能不可见/不可执行；更新失败不污染正在运行的快照；撤销、网络中断、离线策略和同名冲突符合预期；可从备份重建完整技能目录。此阶段单独估算工作量，不包含在只读知识库排期内。

### 阶段 D：长期记忆

补齐平台身份、统一生命周期、持久同步队列、写入对账、抽取质量及删除闭环后，先对单个可信用户开启，再扩展到其他入口。定时任务使用独立服务主体，不自动写入某个人的偏好。

必须通过：重启不丢已确认待同步轮次；同轮只排队一次；网络结果不明不盲目重复写入；commit 失败可诊断；并发用户和子 Agent 不串记忆；删除后重试不能复活数据；自动推测不能直接发布为共享案例。

### 阶段 E：统一管理验收与精简

验收知识、长期记忆、Skills 均已以 OpenViking 为在线权威源，本地没有独立修改同一内容的入口，编辑和撤销能同步影响后续使用。再依据数周使用结果决定是否退役原 L2 全文会话索引、扩大自动记忆范围或调整存储后端；会话运行状态、执行审计与观测系统仍然保留。

排期粗估：只读技术验证约 1–2 个工程日；包含灰度、权限、导入管理和故障验证的只读正式接入约 1–2 周。多人长期记忆单独估算，取决于身份改造和上游删除/幂等验证，不包含在只读试点承诺内。

## 11. 开工前确认项

- 第一批文档来源、访问人群及允许发送到模型服务的数据范围。
- OpenViking 部署位置、固定版本、模型选择及预算。
- 第一阶段是否仅面向同一可信运维团队；若包含外部用户，先完成租户隔离。
- 原始知识负责人、更新频率、共享案例审核人和备份保留要求。

首批推进范围建议：单可信团队、只读运维知识库、独立内网实例、保留现有检索、自动记忆关闭；随后按阶段完成 Skills 与记忆迁移。最终目标已经确认，不再把“Skills 和长期记忆仍由本地独立管理”作为默认终态。
